精炼回答
Agent测试用例库的构建需要覆盖意图识别、上下文管理、工具调用和响应生成这几个核心环节。和传统软件测试最大的区别在于，Agent是概率性系统，同样的输入可能因为LLM的随机性产生不同输出，这决定了整个测试思路都要变。

对于单元测试，你要针对Agent的各个独立组件设计用例。比如测试LLM的prompt模板是否正确生成、测试工具函数的输入输出是否符合预期、测试记忆模块的存取逻辑。具体像测试一个查询天气的工具函数，输入"北京"应该返回正确格式的天气数据，输入无效城市名要有合理的错误处理。重点是隔离依赖，用mock替代真实的LLM调用和外部API，这样既保证测试的稳定性又能控制成本。

集成测试则要验证完整的对话流程。设计用例时要构建真实场景的多轮对话序列，比如"帮我订明天去上海的机票"这个请求，需要测试Agent能否正确调用航班查询工具、处理多个航班选项、记住用户的偏好、完成预订流程。关键是验证组件间的协作和状态传递是否正常。

测试用例库要包含正常路径、异常路径和边界情况。比如用户输入模糊、上下文断裂、工具调用失败、超时等场景都要覆盖。建议用对话树的方式组织用例，每个分支代表不同的用户意图和系统响应组合。同时要记录每个用例的预期输出，不仅是最终答案，还包括中间步骤的工具调用序列和推理链路，这样能更精准地定位问题。

扩展分析
Agent系统的测试确实比传统应用更有挑战性，主要体现在三个方面。首先是非确定性问题，同样的输入可能因为LLM的随机性产生不同输出；其次是外部依赖复杂，Agent往往要调用多个第三方API和工具；最后是多步推理的可验证性，很难用简单的断言判断中间推理过程是否合理。这些特点决定了我们需要建立一套完全不同于传统软件的测试体系。

按照测试粒度从细到粗，我会建立三层防护。最底层的单元测试聚焦在隔离环境下验证单个组件，比如Prompt生成器、工具函数、记忆存储模块各自的正确性；中间层的集成测试验证组件协作，比如Agent接收指令后能否正确编排工具调用顺序、上下文能否正常传递；最外层的端到端测试模拟真实用户场景，验证完整对话链路。这个分层既体现了测试金字塔原则，也符合Agent系统的技术架构。

用例库的设计要从三个维度考虑。功能覆盖要确保Agent的核心能力都被测试到，比如意图识别、参数提取、工具选择这些基础能力；边界探测关注临界状态，像多轮对话的上下文窗口即将溢出时怎么处理、用户突然切换话题时能否正确重置状态；异常处理则要模拟各种失败场景，工具调用超时、返回格式异常、用户输入不合法等情况下Agent的降级策略是否生效。拿智能客服Agent举例，功能覆盖要测试它能否理解"退货"这个意图并提取订单号；边界探测要测试当用户说"我那个上周买的东西"这种模糊表达时，Agent能否通过多轮对话澄清；异常处理要测试当订单查询接口挂了的时候，Agent是否能优雅降级，比如引导用户提供订单号让人工客服跟进。

Agent测试的第一个难点是如何验证正确性。比如用户问"帮我推荐个手机"，Agent回复iPhone 15和回复小米14，哪个算对？这不像单元测试里断言assertEquals那么简单。第二个难点是推理过程的黑盒特性，从用户输入到最终输出中间可能调用了五个工具、经过三轮思考，这个链路怎么确保每一步都合理？第三个难点是状态爆炸，多轮对话会产生指数级的状态组合，用户可能随时切换话题、补充条件或者推翻之前的要求，这些分支你不可能全部穷举测试。

测试用例库的组织要按照从原子到复合的思路分层。最底层是原子能力用例，测试Agent的基础技能是否达标，比如意图识别能不能区分"查询订单"和"取消订单"，参数提取能不能从"我要去北京"里提取出目的地。这层用例的特点是输入输出都很明确，可以用传统的断言来验证。往上一层是组合能力用例，测试Agent能否正确编排多个工具。拿搜索场景举例，用户说"帮我找最近的川菜馆，人均100以内"，Agent需要先调用地理位置服务获取当前坐标，再调用餐厅搜索接口过滤价格，最后按距离排序。这层用例要验证的不只是每个工具调用是否成功，更要验证调用顺序和参数传递是否合理。我会记录完整的工具调用序列，作为Golden Path保存下来。后续回归测试时，如果Agent选择了不同的工具组合，不一定是错的，但需要人工review确认新路径是否更优。

最上层是场景化用例，模拟真实用户的完整任务流程。比如测试智能运维Agent，用户报障说"网站打不开"，Agent要先询问是哪个环境的问题，然后调用监控工具检查服务状态，发现是数据库连接池满了，再执行重启操作并验证恢复。这个场景涉及多轮对话的上下文保持、诊断推理的正确性、操作执行的安全性，是个典型的端到端测试案例。

Mock策略与隔离测试
单元测试阶段，我会把Agent拆解成几个可独立验证的模块。Prompt构造器是一个测试重点，需要验证不同场景下生成的Prompt是否包含必要的上下文和约束条件。这里可以用模板匹配或者关键词检查来断言，比如测试"查询历史订单"这个意图，生成的Prompt里必须包含用户ID和时间范围这两个占位符。

对于LLM的调用，我会构建一个ResponseStub层，预先录制各种典型的模型输出。比如测试Tool Calling功能时，Mock一个包含函数调用JSON的响应；测试异常处理时，Mock一个格式错误的响应。关键是要控制随机性，通过固定temperature和seed参数，或者直接用录制回放的方式保证测试可复现。生产环境我会保留LLM请求响应的日志，定期从中提取真实case补充到Mock库里。

class MockLLM:
    def __init__(self, response):
        self.response = response
    
    def generate(self, prompt):
        return self.response

# 测试工具调用解析逻辑
mock_llm = MockLLM('{"tool": "search", "query": "北京天气"}')
agent = Agent(llm=mock_llm)
result = agent.process("今天北京天气怎么样")
assert result.tool_name == "search"

固定响应的问题是不够灵活，测试复杂流程时需要根据不同Prompt返回不同内容。这时候我会用响应模板的方式，根据Prompt中的关键词匹配返回内容：

class TemplateBasedMockLLM:
    def __init__(self):
        self.templates = {
            "天气": '{"tool": "weather_api", "location": "{city}"}',
            "订单": '{"tool": "order_query", "order_id": "{id}"}'
        }
    
    def generate(self, prompt):
        for keyword, template in self.templates.items():
            if keyword in prompt:
                # 从prompt提取参数填充模板
                return self._fill_template(template, prompt)
        return "我不太理解你的问题"
python
对于需要真实语义理解的测试场景，可以用小模型做本地Mock。像测试多轮对话的上下文理解能力，固定响应和模板都不够用，这时候用个几百M的小模型既能保证基本的推理能力，又不会像调用GPT-4那样慢和贵。本地小模型的推理延迟在100ms左右，跑几百个测试用例也就几分钟，完全能接入到CI流程里。

工具函数的单元测试要覆盖正常路径和异常分支。测试价格查询工具时，正常路径是输入商品ID返回价格，但我还会测试ID不存在、价格为0、价格是负数、返回超时这些异常分支。更细致的还要测试浮点数精度问题，比如价格9.99在经过计算后会不会变成9.989999：

import pytest
from unittest.mock import Mock

class WeatherTool:
    def __init__(self, api_client):
        self.api_client = api_client
    
    def execute(self, city):
        if not city or not isinstance(city, str):
            raise ValueError("城市名称无效")
        
        response = self.api_client.get_weather(city)
        return {
            "city": city,
            "temperature": response["temp"],
            "condition": response["weather"]
        }

@pytest.fixture
def mock_api_client():
    client = Mock()
    client.get_weather.return_value = {
        "temp": 25,
        "weather": "晴天"
    }
    return client

def test_weather_tool_normal_case(mock_api_client):
    tool = WeatherTool(mock_api_client)
    result = tool.execute("北京")
    
    assert result["city"] == "北京"
    assert result["temperature"] == 25
    mock_api_client.get_weather.assert_called_once_with("北京")

def test_weather_tool_invalid_input():
    tool = WeatherTool(Mock())
    with pytest.raises(ValueError):
        tool.execute("")
python
这个测试用Mock隔离了外部API依赖，验证了正常路径和异常处理，还通过assert_called_once_with确认参数传递正确。这种隔离策略保证了单元测试的稳定性和速度。

Prompt模板的测试重点验证变量替换和条件分支：

class PromptBuilder:
    def build_query_prompt(self, user_input, context=None):
        base = f"用户问题：{user_input}\n"
        if context:
            base += f"对话历史：{context}\n"
        base += "请分析用户意图并选择合适的工具。"
        return base

def test_prompt_with_context():
    builder = PromptBuilder()
    prompt = builder.build_query_prompt(
        "上次那个订单发了吗",
        context="用户之前查询了订单12345"
    )
    
    assert "用户问题：上次那个订单发了吗" in prompt
    assert "对话历史：用户之前查询了订单12345" in prompt
    assert "请分析用户意图" in prompt

集成测试与工作流验证
集成测试阶段，我关注的是组件之间的协作契约是否履行。比如测试一个包含记忆模块的Agent，需要验证第一轮对话存储的用户偏好，在第二轮对话时能否正确读取并应用。这不仅要测试存储接口调用成功，还要测试检索的优先级逻辑，当记忆里有三条相关信息时，Agent是否能选出最相关的那条。

端到端场景测试要接入真实的API服务，但会搭建一个沙盒环境避免影响线上数据。拿电商场景举例，测试退货流程时需要先创建一个测试订单，然后让Agent执行完整的退货操作，最后验证订单状态、库存数量、退款金额这些关联数据是否都正确变更。这个过程还要测试异常恢复能力，比如中途网络超时，Agent能否记住执行到哪一步，重试时不会重复扣款。

class AgentIntegrationTest:

这个测试不仅验证了每轮的工具选择，还检查了记忆模块是否正确保存上下文。第二轮对话Agent能理解"开车要多久"是在问北京到上海的车程，说明上下文传递是正常的。

Agent的能力是持续迭代的，可能今天加了一个新工具，明天优化了Prompt策略。回归测试我会维护一个Benchmark Suite，包含代表性的对话场景和预期的表现基线。每次模型升级或者逻辑变更后，跑一遍这个Suite，对比关键指标是否退化。比如任务完成率不能降低5个百分点，平均响应轮次不能增加1轮，这些阈值需要根据业务场景校准。

测试数据与用例组织
我会建立一个分层的数据集体系。第一层是Seed Cases，大概几十个精心设计的核心场景，每个case都有详细的执行步骤和验证点标注，这是保证基本功能不出错的防线。第二层是Synthetic Data，通过模板和规则生成的大量变体，比如同一个意图用不同的表达方式、相同的流程在不同的参数组合下执行，这层数据用来做覆盖度测试。第三层是Production Samples，从线上日志采样的真实用户对话，这些数据最有价值但需要脱敏处理，主要用来发现你设计用例时想不到的长尾问题。

测试用例库的组织按照粒度分层管理，这样既能保证测试覆盖度，又能控制执行时间：

tests/
├── unit/
│   ├── test_tools.py          # 工具函数测试
│   ├── test_prompts.py         # Prompt模板测试
│   └── test_memory.py          # 记忆模块测试
├── integration/
│   ├── test_workflows.py       # 工作流测试
│   └── test_tool_chains.py     # 工具链测试
├── e2e/
│   ├── scenarios/
│   │   ├── customer_service.json
│   │   └── order_management.json
│   └── test_scenarios.py
└── fixtures/
    ├── mock_responses/
    └── test_data/
按测试粒度分层组织，unit目录下的测试运行最快，每次提交代码都会跑；integration测试相对慢一些，在合并前执行；e2e测试最重，定期跑或者发版前跑。scenarios目录用JSON定义测试场景，这样产品同学也能参与用例设计。

自动化测试流程要配置多级流水线，在不同阶段运行不同粒度的测试：

# .github/workflows/test.yml
name: Agent Tests

on: [push, pull_request]

jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - name: Run unit tests
        run: pytest tests/unit -v --cov
      
  integration-tests:
    needs: unit-tests
    runs-on: ubuntu-latest
    steps:
      - name: Run integration tests
        run: pytest tests/integration -v
      
  e2e-tests:
    if: github.event_name == 'pull_request'
    needs: integration-tests
    steps:
      - name: Run E2E scenarios
        run: pytest tests/e2e --timeout=300
yaml
unit-tests每次都跑，几分钟就能出结果；integration-tests只在单元测试通过后才执行，避免浪费资源；e2e-tests只在PR阶段运行，因为比较耗时而且可能调用外部服务。

成本控制与效果评估
测试成本主要来自LLM调用和外部API请求。单元测试和大部分集成测试都用本地Mock，完全不调用真实LLM。只有标记为cloud的测试用例才会真正调用GPT-4，这些用例主要验证最新模型的能力是否符合预期。

对于需要调用真实LLM的测试，我会建立请求响应的缓存层。相同的Prompt第二次运行时直接返回缓存结果，既保证了测试可复现，又省了API费用：

import hashlib
import json
import os

class CachedLLM:
    def __init__(self, real_llm, cache_dir):
        self.real_llm = real_llm
        self.cache_dir = cache_dir
    
    def generate(self, prompt):
        cache_key = hashlib.md5(prompt.encode()).hexdigest()
        cache_file = f"{self.cache_dir}/{cache_key}.json"
        
        if os.path.exists(cache_file):
            with open(cache_file) as f:
                return json.load(f)["response"]
        
        response = self.real_llm.generate(prompt)
        with open(cache_file, 'w') as f:
            json.dump({"prompt": prompt, "response": response}, f)
        
        return response
python
对于大规模的测试用例集，日常回归时可以采样运行，比如每个类别抽取20%的用例。完整测试放在发版前的集成阶段。我之前参与的一个项目，测试用例库有800多个case，如果每次都跑完需要2小时，采样策略让日常测试缩短到15分钟，大大提升了迭代效率。

任务完成率是最直接的指标，但要区分简单任务和复杂任务分别统计。响应准确性我会用两个维度衡量，一是事实性正确，工具返回的数据是否准确；二是语义合理性，Agent的回复是否符合对话上下文。Token消耗关系到成本，需要监控平均每次对话的输入输出Token数，如果突然飙升可能是Prompt设计有问题或者陷入了死循环。延迟指标要拆分成思考时间和工具调用时间，这样能定位性能瓶颈在哪。

除了这些量化指标，我还会关注一些定性的观察。比如Agent的拒绝率，面对超出能力范围的请求能否优雅拒绝而不是胡乱回答；再比如工具选择的合理性，明明有现成的API可以调用，却选择了让LLM硬算，这种情况说明编排逻辑有优化空间。

进阶思考
真正优秀的Agent测试体系会在设计阶段就考虑可测试性。比如把Prompt模板独立成可配置的资源文件，这样测试时可以快速切换不同版本对比效果；再比如工具调用接口设计时就定义清晰的输入输出Schema，让Mock和真实调用能无缝替换。这种测试左移的思维能让质量保障的关口前置，不是等Agent开发完了再想怎么测，而是在架构设计时就内建了可测试性。

Prompt质量的测试比较特殊，因为Prompt不是代码，很难用传统的单元测试方法去验证。对于结构化的Prompt，我会检查必要的占位符是否都被正确填充、Few-shot示例的格式是否一致、指令的逻辑链条是否完整。这些可以通过正则表达式或者模板引擎的校验机制来自动化。但最终还是要通过Agent的实际表现来反推Prompt质量。我会维护一个Prompt版本库，每次改动Prompt后跑一遍回归测试集，对比任务完成率、工具调用准确率这些指标是否有提升。如果新版本在某些case上表现变差，需要分析是Prompt表达不够清晰还是约束条件有歧义。

幻觉问题在测试阶段要分两步处理。第一步是识别容易出现幻觉的场景，比如需要精确数值计算的场景、涉及时效性信息的查询、要求引用具体来源的问答，这些场景我会设计专门的测试用例，验证Agent是否优先调用工具而不是让LLM直接生成答案。第二步是对LLM生成的内容建立事实性检查机制。如果Agent回复了一个可验证的事实，测试框架会自动调用知识库或者搜索API做交叉验证。比如Agent说某个订单的物流状态是"已签收"，测试脚本会真正查询一次物流接口，确认状态确实匹配。

测试用例库不是一次性建完的，而是随着Agent能力迭代持续积累的。我会建立用例的元数据管理，每个用例标记它测试的能力点、涉及的组件、预期的推理链路，这样既方便回归测试时快速定位，也能通过用例覆盖度分析发现测试盲区。当线上监控发现某类场景的失败率突然上升，我会把这些失败case自动提取出来，脱敏后加入测试集。这样测试用例库就在持续演进，覆盖的是真实用户遇到的问题而不是工程师臆想的场景。

测试和监控应该是一体的。测试用例库解决的是已知问题的验证，但线上环境的复杂度远超测试环境。我会建立Agent的可观测性体系，每次对话都记录完整的推理链路，包括接收到什么输入、生成了什么Prompt、调用了哪些工具、每个工具返回了什么、最终输出是什么。这些日志不仅用于问题排查，还能反哺测试用例库，形成测试-监控-优化的闭环。

对于主观性较强的质量维度，可以用LLM-as-a-Judge的方式。让另一个LLM作为评判者，给它提供评分标准和待评估的Agent输出，让它判断质量。比如评估客服Agent的回复是否专业、是否解决了用户问题、语气是否友好，这些很难写代码判断，但可以让GPT-4按照标准打分。当然这种方式成本比较高，每个测试用例都要多调用一次LLM，而且Judge本身也可能有偏见，需要通过人工抽样验证Judge的评分是否靠谱。

再完善的自动化测试也无法完全替代人类判断。我会建立一个人类反馈的机制，定期从线上对话中抽样，让领域专家评审Agent的表现。这些专家反馈会标注在对话记录上，比如某个回复虽然事实正确但表达方式不够通俗，或者某个工具选择虽然能完成任务但不是最优路径。这些标注数据会沉淀下来，一方面补充到测试用例库作为Golden Cases，另一方面可以用来微调模型或者优化Prompt策略，形成线上运行-人工评审-提取问题-优化系统-回归测试-重新上线的持续改进循环。

测试策略的核心是分层防护。用大量便宜的本地测试保证基础质量，用少量昂贵的云端测试验证关键路径，这样既控制了成本，又不会漏掉重要问题。整体来说，Agent测试是个系统工程，需要在技术手段、成本控制和质量保障之间找到平衡点，最终目标是建立一个可持续演进的质量体系。
