# 什么是对话历史窗口？保留多少轮对话合适？

> **难度**: 中等 | **分类**: AI Agent理论与框架 | **标签**: AI

## 核心定义
- **对话历史窗口**：多轮对话中保留的最近历史消息数量，类似人的短期工作记忆。
- **核心限制**：受限于模型Token上限、计算成本和推理延迟，不能无限保留所有历史。

## 机制与原理
- **Token预算分配**：模型总上下文需同时容纳系统提示词、历史对话、当前输入及预留输出空间。例如4K模型扣除提示词和输出预留后，实际留给历史的可能仅剩约2500 token。
- **Token不对称性**：用户简短的提问（十几token）可能引发模型长篇回复（数百token），5轮对话极易消耗2000+ token。
- **滑动窗口与摘要**：基础策略为FIFO队列保留最近N轮；进阶策略为保留System Prompt和最近几轮，对早期历史调用模型进行摘要压缩。
- **Lost in the middle现象**：即使使用128K/200K长上下文模型，塞满上下文也会导致模型注意力衰减，对中间部分信息提取能力显著下降。
- **Agent场景复杂性**：Agent的窗口不仅包含用户对话，还包含思考过程和工具调用结果。通常采用分层设计：用户侧保留简洁交互，Agent侧保留完整推理Trace。

## 对比速记
- **短期记忆 vs 长期记忆**：对话窗口属于短期工作记忆，处理当前任务上下文；长期记忆依赖RAG和向量数据库，解决跨会话的知识检索问题。
- **固定截断 vs 动态调整**：固定截断（FIFO）实现简单但易丢失关键信息；动态调整会根据话题切换（语义相似度骤降）清空历史，或根据消息重要性（包含订单号等关键实体）优先保留。

## 代码示例
```java
public class ConversationWindow {
    private final int maxRounds;
    private final Deque<Message> messages;

    public ConversationWindow(int maxRounds) {
        this.maxRounds = maxRounds;
        this.messages = new LinkedList<>();
    }

    public void addMessage(Message message) {
        // 一轮对话包含用户消息和助手回复，所以是2倍
        if (messages.size() >= maxRounds * 2) {
            messages.pollFirst(); // 移除最早的用户消息
            messages.pollFirst(); // 移除对应的助手回复
        }
        messages.addLast(message);
    }

    public List<Message> getContext() {
        return new ArrayList<>(messages);
    }
}
```

## 工程要点
- **场景化配置**：简单客服/咨询聚焦独立（3-5轮），复杂编程/专业咨询强依赖上下文（10-20轮）。
- **分级保留机制**：System Prompt永远保留，最近3轮强制保留，中间历史按优先级字段（priority）或实体重要性动态淘汰。
- **成本与延迟权衡**：窗口过大不仅线性增加Token费用，输入从2K增至4K时首Token延迟也会增加20%-30%。
- **会话恢复机制**：将窗口内容序列化存入Redis，24小时内恢复完整窗口，超时则仅恢复关键信息摘要。
- **数据驱动调优**：通过分析用户对话轮次分布（如80%在5轮内结束）设定初始窗口，灰度上线并监控截断率、平均Token消耗和多轮完成率。
