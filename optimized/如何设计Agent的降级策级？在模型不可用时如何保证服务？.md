# 如何设计Agent的降级策级？在模型不可用时如何保证服务？

> **难度**: 中等 | **分类**: AI Agent理论与框架 | **标签**: AI

## 核心回答

Agent降级策略的核心是建立多层防护机制。当主力大模型不可用时，系统需要像多米诺骨牌的最后一道防线那样，确保服务不会彻底崩溃。这里面最关键的是三个层次的递进式降级：模型层降级、能力层降级和服务层降级。

模型层降级是第一道防线。当GPT-4响应慢或者限流时，立刻切换到GPT-3.5或者本地部署的Llama这样的开源模型。这要求你在架构设计时就做好模型抽象层，通过统一接口管理多个模型实例，让上层业务逻辑感知不到底层模型的变化。技术实现上需要维护一个模型池，通过心跳检测各自的可用性，优先选择延迟低、错误率低的模型。

当模型完全不可用时，能力层降级就派上用场了。这时候Agent要退化为基于规则的系统，使用预定义的决策树或模板来处理常见场景。比如客服Agent原本能理解"我想买件适合约会穿的连衣裙"这种模糊需求，降级后只能识别"连衣裙"这个关键词，然后返回预设的热门商品列表。你需要提前梳理出高频场景，像查订单、退换货这些核心流程，都准备好基于关键词匹配的兜底话术。

最底层是服务层降级，这是最后的防线。复杂的多步推理简化为单步查询，工具调用降级为直接返回cached结果。比如原本需要联网搜索的问答，降级后直接使用知识库检索。即使规则引擎也无法处理时，至少要返回友好的错误提示，让用户知道系统在尽力服务而不是崩溃了。

技术实现上建议采用熔断器模式监控模型健康状态，设置超时阈值和错误率阈值。同时维护一个降级决策引擎，根据当前故障等级自动选择降级方案。关键是要预埋监控指标，实时追踪各层级的可用性，并在降级时明确告知用户当前服务能力受限，管理好用户预期。

## 扩展分析

Agent降级的特殊性与分层设计
在聊具体方案前，我想先说说为什么Agent的降级比传统服务更复杂。传统降级更多是性能问题，比如数据库压力大就关闭一些非核心功能，这个落差用户基本无感知。但Agent降级要面对的是能力边界的突变——模型从"能理解复杂意图"直接退化到"只能执行固定逻辑"，这个落差如果处理不当，用户会觉得系统突然变傻了。

Agent系统有三个让降级变复杂的特性。它是有状态的，用户可能已经进行了五轮对话，突然降级不能让前面的上下文全丢。它是多轮交互的，不像HTTP请求那样无状态，每次调用都需要考虑历史信息。最要命的是它依赖大模型API这个外部服务，你没法像控制自己数据库那样精准掌控它的可用性。这三个特点决定了降级不能简单粗暴，必须有平滑过渡的机制。

分层设计的核心思路是让每一层对应不同的故障程度。模型层降级处理的是暂时性抖动，比如某个provider突然响应变慢，这时候切换到备用模型就能解决问题。我会设计一个ModelRouter组件，通过配置文件管理多个模型的优先级和健康状态。具体来说就是在启动时初始化多个ModelClient实例，每个对应不同的provider，运行时通过心跳检测各自的可用性。关键是要统一输入输出格式，把prompt和返回结果做好适配，让上层业务逻辑感知不到底层模型的变化。

能力层降级的复杂度在于如何设计规则引擎。我的思路是把常见意图抽象成决策树，比如用户说"我的订单呢"，通过关键词"订单"定位到查询订单流程，然后提示用户输入订单号。这里不要陷入规则引擎的实现细节，重点是提前梳理场景这个思路。我会拉着产品和运营同学一起过一遍高频对话记录，把能用规则覆盖的场景都抽出来，形成一个兜底话术库。

这个决策树看起来简单，但实际落地时会遇到一个大坑：状态管理。降级过程中最容易出问题的就是丢失上下文。用户已经告诉Agent他想买红色连衣裙，进行到选择尺码环节时模型挂了，降级后不能让用户重新说一遍颜色偏好。这时候需要把关键信息持久化，可以存到Redis这样的缓存里，key是会话ID，value是结构化的上下文数据。

```java
public class ConversationContext implements Serializable {
    private String sessionId;
    private Map<String, String> slots; // 存储已收集的槽位信息
    private List<Message> history; // 对话历史
    private DegradationLevel currentLevel; // 当前降级级别
    private long lastUpdateTime;

    public void saveToCache() {
        redisTemplate.opsForValue().set(
            "session:" + sessionId,
            JSON.toJSONString(this),
            Duration.ofHours(1)
        );
    }

    public void restoreFromCache(String sessionId) {
        String json = redisTemplate.opsForValue().get("session:" + sessionId);
        if (json != null) {
            ConversationContext ctx = JSON.parseObject(json, ConversationContext.class);
            this.slots = ctx.getSlots();
            this.history = ctx.getHistory();
        }
    }
}
```

这段代码的关键是把上下文设计成可序列化的结构，并且考虑了过期时间。降级后切换到规则引擎时，可以从slots里拿到用户之前提到的偏好信息，保证对话的连续性。

降级触发本质上是一个实时决策过程，需要监控三类指标。第一类是延迟分位数，不能只看平均值，要看P99延迟是否超过阈值，因为长尾请求往往是故障的先兆。比如模型调用的P99延迟从1秒突然跳到5秒，即使平均延迟还在2秒以内，也说明有问题了。第二类是错误类型分布，超时错误和限流错误要分开统计，前者可能是模型服务卡顿，后者说明需要立刻切换。第三类是业务成功率，即使模型返回了结果，但如果用户频繁反馈答非所问，也说明需要降级。

这些指标的阈值不是拍脑袋定的，初期可以根据历史数据的分位数来设定，比如取过去一个月P95延迟的1.5倍作为超时阈值。上线后通过AB测试持续调优，观察不同阈值下的用户留存率和投诉率。我会用滑动窗口统计这些指标，避免偶发抖动导致的误判。比如采用60秒的窗口期，只有连续三个窗口都超过阈值才真正触发降级。

降级后的用户体验优化
降级不只是技术问题，更是用户体验问题。很多候选人回答到技术实现就停了，但如果你能主动说"降级不只是技术问题，更是用户体验问题"，会让面试官印象深刻。当触发降级时，我会在响应里加一个标识告诉用户当前能力受限。比如原本Agent能主动推荐商品，降级后只能回答具体问题，就可以提示："当前处于简化模式，我可以帮您查询订单或解答常见问题。"这个提示要自然，不能让用户感觉系统在甩锅，而是让他理解当前能做什么、不能做什么。

拿智能客服Agent举个具体的例子。平时它能理解用户的复杂问题，比如"我上周买的那个东西怎么还没到，能帮我查查吗"，模型能从对话历史里定位到订单。降级后只能处理结构化的查询，用户需要提供订单号才能查询。这时候Agent会主动引导用户："为了更快帮您查询，请提供您的订单号。"这样既完成了降级，又不会让用户觉得是系统故障。这个例子的巧妙之处在于，你把技术降级包装成了用户引导，体现了对产品思维的理解。

推荐场景的降级相对特殊，因为用户对推荐结果的容忍度更高。正常情况下Agent能根据用户的浏览历史、兴趣标签做个性化推荐，降级后可以直接返回热销榜单或者按类目推荐。关键是要在返回结果里埋个标识，监控降级后的点击率是否明显下降。如果下降太多，说明降级方案需要优化，比如可以用协同过滤这种轻量算法兜底，而不是直接返回静态榜单。

更进一步，可以提供降级期间的补偿机制。降级时无法完成的复杂查询，可以引导用户留下联系方式，等服务恢复后主动回复。我会记录降级期间未完成的会话，等模型恢复后异步处理，通过短信或推送通知用户。这个方案不一定要在面试里详细实现，但提出这个思路就足以让面试官觉得你考虑得很周全。

```java
public class FallbackResponse {
    private String content;
    private boolean isDegraded; // 标识当前是否降级
    private DegradationLevel level;
    private String userHint; // 给用户的提示语

    public static FallbackResponse createDegradedResponse(
        String content,
        DegradationLevel level
    ) {
        FallbackResponse response = new FallbackResponse();
        response.content = content;
        response.isDegraded = true;
        response.level = level;

        // 根据降级级别设置不同的提示语
        switch (level) {
            case MODEL_SWITCH:
                response.userHint = "当前使用简化模式为您服务";
                break;
            case RULE_ENGINE:
                response.userHint = "当前仅支持基础查询功能";
                break;
            default:
                response.userHint = "服务繁忙，您可以稍后再试";
        }

        return response;
    }
}
```

降级不是单向的，需要有自动恢复的能力。当监控发现模型服务恢复正常后，逐步提升降级级别，从服务层恢复到能力层，再恢复到模型层。这个过程要平滑，不能一下子全量切回去导致新的压力峰值。可以用灰度的方式，先让10%的流量走主力模型，观察稳定后再逐步放量。我会在监控面板上实时展示当前降级状态，让运维同学能快速判断系统健康度。

降级策略的测试不能等到生产环境故障时才验证，我会提前做混沌工程演练。具体来说就是在测试环境定期模拟模型故障，比如用脚本随机杀掉模型服务的连接，观察系统是否能按预期降级。

成本与性能的平衡
维护多个模型备份肯定会增加成本，我会评估各个模型的调用量和单价，优先选择性价比高的备用方案。比如大部分场景用云端API，只在核心场景部署一个小规模的本地模型兜底，这样既保证了可用性又控制了成本。从GPT-4切到GPT-3.5虽然能快速止损，但效果肯定有损失。我会根据业务优先级来决定哪些场景可以接受这个降级。

如果是金融客服询问账户余额这种简单查询，降级影响不大。但如果是理解复杂的投资咨询需求，降级后可能答非所问，这时候宁可慢一点也要等主模型恢复，或者直接告诉用户转人工。这种细节能让面试官感受到你在权衡不同选择的利弊，而不是一刀切地降级。

实际场景往往不是单一降级，而是多个策略叠加。比如在大促期间，可能同时触发流量降级和模型降级。流量降级是指对非VIP用户限制Agent的使用频率，减轻模型压力；模型降级是切换到更快但效果稍差的模型。这两个策略要配合使用，可以在配置里设置优先级，比如先尝试模型切换，如果整体流量还是过高再启动流量限制。关键是要有一个降级决策引擎来协调这些策略，避免多个开关同时触发导致系统行为不可预测。

阈值需要根据业务场景和用户容忍度来定。我会先看历史数据的分布，比如P95延迟是多少，然后做AB测试，观察不同阈值下的用户留存率和投诉率。这个回答既展现了数据驱动思维，又暗示这是个需要持续优化的过程。恢复机制也不能一步到位，要用灰度放量的方式。先让小部分流量走主模型，观察稳定性指标，再逐步扩大比例。

就算你没做过Agent降级，也可以从其他高可用设计的经历里找相似点。比如你做过API网关的限流熔断，可以说："虽然之前没做过Agent降级，但我在网关层实现过类似的熔断机制，核心思路是通过监控指标实时调整流量策略。"然后简单类比一下两者的共通点，这样既诚实又能展现你的迁移学习能力。面试官不会期待校招生有完整的Agent项目经验，但他想看到你能把已有经验抽象出来，应用到新场景里。这种全局观才是面试官最看重的，也是把你和那些只会背八股文的候选人区分开的关键。
