# ReWOO（Reasoning WithOut Observation）模式与ReAct有什么区别？各自的适用场景？

> **难度**: 中等 | **分类**: AI Agent理论与框架 | **标签**: AI

## 核心回答

ReWOO与ReAct的核心区别在于执行模式。ReAct是交替式执行，每次推理后立即观察工具结果再继续思考，形成"思考-行动-观察"的循环；而ReWOO采用规划与执行分离的策略，先一次性制定完整的推理计划和工具调用序列，然后批量执行所有工具调用，最后统一处理结果得出答案。

这种差异带来明显的性能特征。ReWOO通过预先规划，可以并行调用多个工具，大幅减少LLM调用次数和总体延迟，在需要多步工具协作的场景中效率更高，比如需要同时查询数据库、调用API、检索文档的复杂分析任务。但ReWOO的缺点是缺乏中间反馈，如果初始规划有误或工具返回异常，难以动态调整。

ReAct则更加灵活自适应，每步都能根据实际观察结果调整策略，适合处理不确定性高、需要探索性推理的任务，比如调试代码问题、多轮对话交互、需要根据中间结果决定下一步的场景。代价是频繁的LLM调用导致响应慢、成本高。选择建议很明确：任务流程清晰、工具调用路径可预测时用ReWOO获取性能优势；需要动态决策、处理异常情况、或任务目标模糊时用ReAct保证准确性。实际项目中也可以混合使用，先用ReWOO处理标准流程，遇到异常再切换到ReAct模式。

## 扩展分析

工作机制深度解析
要真正理解两种模式的区别，得先搞清楚它们的工作机制。ReAct本质上是一个循环过程，每个循环包含三个步骤：首先大模型基于当前状态生成Thought也就是思考，决定下一步要做什么；然后执行Action也就是行动，调用具体的工具比如搜索引擎或数据库；最后获得Observation也就是观察结果，把工具返回的信息喂给大模型作为下一轮思考的输入。这里的关键点是每次行动后必须等待大模型处理观察结果才能继续，这个等待就是性能瓶颈的根源。

举个具体例子会更清楚。假设用户问"北京今天天气怎么样，适合穿什么衣服"，ReAct的执行流程是这样的：第一轮，大模型思考后决定调用天气查询工具，发起API调用查到北京今天15度多云；第二轮，大模型基于天气信息思考后决定调用穿衣建议工具，获取推荐结果；第三轮，大模型综合前面的信息生成最终回答。这个过程中大模型被调用了三次，每次都要等待几百毫秒甚至几秒的推理时间，而且这些调用是完全串行的，没法并行优化。

ReWOO的设计思路就是把推理和执行分开。它引入了三个核心组件：Planner规划器负责一次性规划出所有需要执行的步骤，Worker执行器负责并行调用所有工具，Solver求解器负责基于全部执行结果给出最终答案。Planner的输出不仅仅是步骤列表，而是一个带有依赖关系的执行计划。

还是刚才那个天气穿衣的例子，用ReWOO来处理的话，Planner会生成这样的计划：步骤一调用天气查询API获取北京天气，步骤二调用穿衣建议API（这一步依赖步骤一的结果）。Worker拿到这个计划后发现步骤二依赖步骤一，会先执行步骤一，拿到结果后立即执行步骤二，整个过程只需要调用一次大模型来规划，一次大模型来总结，中间的工具调用完全不需要大模型参与。如果有多个独立的工具调用，Worker还能并行执行，这就是性能提升的来源。

Plan: 步骤1查天气
步骤2查穿衣建议

Worker执行步骤1

Worker执行步骤2

Solver综合结果

返回答案

根据ReWOO论文的测试数据，在HotpotQA这种需要多步推理的数据集上，ReAct平均每个问题要调用6-8次大模型，而ReWOO只需要2次，一次规划一次总结。在API调用成本上，假设每次GPT-4调用成本0.03美元，ReAct处理一千个问题要花180-240美元，ReWOO只需要60美元。延迟方面更明显，ReAct因为串行调用，总耗时是所有步骤的累加，而ReWOO的并行能力让总耗时接近最慢那个工具的响应时间。

但ReWOO最大的问题是缺乏中间反馈的灵活性。因为所有步骤在开始执行前就规划好了，如果某个工具返回了异常结果或者空数据，后续步骤无法根据实际情况调整。比如查询某个商品库存，如果接口返回商品不存在，ReAct可以立即改为搜索类似商品，而ReWOO已经规划好要查这个商品的价格、评论等信息，这些调用都会失败，最后Solver拿到一堆错误信息也很难给出有意义的答案。

这种对比用具体场景来说明会更清楚。拿技术文档问答举例，用户问"如何配置Redis集群的主从复制"，ReAct可以先搜索Redis集群配置文档，发现文档里提到了哨兵模式，然后决定进一步搜索哨兵模式的详细配置，这种探索式的推理很难提前规划。而如果是生成标准化的商品分析报告，需要的数据源是固定的（销量、库存、用户评分、价格趋势），这种场景ReWOO就很合适，可以一次性规划好所有查询并行执行。

实践选型与工程落地
实际项目中怎么选择呢？我会从三个维度来评估选哪种模式：任务的可预测性、对响应时延的要求、以及成本预算。可预测性高的典型场景比如生成周报分析，需要查询的数据源是固定的销售额、用户增长、热门商品这些维度，这种情况ReWOO的规划能力完全够用，而且能通过并行查询大幅提速。但如果是处理用户投诉工单，用户可能描述得很模糊，需要通过多轮交互逐步定位问题，这时候ReAct的灵活性就是必需的。

延迟要求也是个重要考量。拿内容审核来说，如果是批量审核历史数据，每条处理时间慢一点没关系，这时候用ReWOO并行调用文本检测、图像识别、敏感词过滤这些工具，虽然规划和总结各需要一次大模型调用，但总体吞吐量更高。可要是实时审核用户发布的内容，用户等待超过两秒就会流失，这时候ReAct虽然调用次数多，但第一步检测就能拦截明显违规内容，不用等所有工具都跑完，平均响应时间反而可能更快。

成本控制在真实业务中往往是决定性因素。如果业务量很大，大模型调用成本就成了大头。假设做一个文档问答系统，每天处理十万个问题，ReAct模式平均每个问题调用五次大模型，一个月下来光API费用就得几十万。这种情况即使ReWOO的准确率稍微低一点，但成本只有三分之一，从ROI角度看可能是更合理的选择。实际落地时可以先用ReWOO处理大部分标准问题，把省下来的预算用在ReAct处理那些复杂的边缘case上。

实际开发中我不会非此即彼，而是设计一个路由层来动态选择模式。具体做法是先用轻量级规则做初筛，比如检测用户输入的意图类型，查询类问题走ReWOO通道，探索类问题走ReAct通道。然后在执行过程中加入监控，ReWOO模式下如果检测到某个工具调用失败或返回置信度低，自动触发降级机制切换到ReAct重新执行。这样既能享受ReWOO的性能优势，又能在异常情况下保证服务质量。

```java
public class AgentRouter {

    public AgentResponse process(UserQuery query) {
        // 意图识别
        QueryIntent intent = intentClassifier.classify(query);

        // 路由策略
        if (intent.isPredictable() && intent.getComplexity() < 5) {
            try {
                // 尝试使用ReWOO模式
                ReWOOAgent rewooAgent = new ReWOOAgent();
                AgentResponse response = rewooAgent.execute(query);

                // 检查执行质量
                if (response.getConfidence() > 0.8) {
                    return response;
                }

                // 质量不达标，降级到ReAct
                logger.warn("ReWOO confidence low, fallback to ReAct");
                return fallbackToReAct(query);

            } catch (ToolExecutionException e) {
                // 工具调用失败，降级处理
                return fallbackToReAct(query);
            }
        } else {
            // 不确定性高的任务直接用ReAct
            ReActAgent reactAgent = new ReActAgent();
            return reactAgent.execute(query);
        }
    }

    private AgentResponse fallbackToReAct(UserQuery query) {
        ReActAgent reactAgent = new ReActAgent();
        return reactAgent.execute(query);
    }
}
```

对于ReWOO模式，因为规划结果是确定的，可以对相同类型的任务缓存执行计划，比如所有商品分析请求的规划逻辑都差不多，只是参数不同，这样能省掉规划阶段的大模型调用。而ReAct因为每步都依赖上一步结果，缓存的粒度只能到工具调用层面，但可以缓存工具的返回结果，比如某个商品的详情在五分钟内不会变化，重复查询可以直接返回缓存。

重试机制也要区别对待。ReWOO的重试要谨慎，因为重新规划的成本很高，一般只在工具调用层面做重试，比如某个API超时了就重试三次。但ReAct的重试策略可以更灵活，如果某步行动失败，可以让大模型基于失败信息重新思考换个方向，这本身就是ReAct的优势所在。

拿电商场景举例，商品推荐系统适合用ReWOO，因为推荐逻辑相对固定，无非是查用户画像、查浏览历史、查协同过滤结果这几个步骤，规划一次并行执行效率最高。但客服对话就得用ReAct，因为用户可能随时转换话题，从咨询商品跳到投诉物流再到申请退款，每一步都要根据用户的实际回复来决定下一步行动。订单异常处理可以混合使用，先用ReWOO快速检查订单状态、物流信息、支付记录这些标准项，如果发现异常再切换到ReAct模式进行深度排查。

技术权衡与演进思考
评估ROI时不能只谈技术指标，要把业务价值算进去。我会看三个维度的成本收益比：技术成本包括大模型API费用、开发调试时间、系统维护复杂度；业务收益要看对核心指标的影响，比如智能客服场景，ReAct的灵活性可能让客户满意度提升百分之十，这个提升能转化成多少用户留存和GMV增长；还有风险成本，如果选了ReWOO但实际场景不确定性高导致准确率下降，修复问题的人力成本和用户流失损失可能远超省下的API费用。

Token消耗、延迟、准确率这三个指标往往不可兼得，构成了一个不可能三角。ReWOO牺牲了一部分准确率换取更低的Token消耗和延迟，因为预先规划可能覆盖不了所有边界情况；ReAct追求高准确率但Token消耗和延迟都比较高；如果要优化延迟同时保证准确率，可能就得接受更高的Token消耗，比如用更大的模型或者增加并行度。实际项目中要根据业务的核心诉求来选择优化方向，比如金融风控场景准确率是第一位的，就不能为了省成本牺牲准确性；但如果是内容推荐，用户对准确率的容忍度高一些，优化成本和延迟的优先级就更高。

最近有一些工作在改进ReWOO的局限性，比如引入轻量级的中间检查点，在规划的关键节点插入验证步骤，如果发现执行偏离预期就触发重新规划。还有研究探索自适应规划深度，根据任务复杂度动态决定规划几步，简单任务用浅层规划降低overhead，复杂任务才做深度规划。这些改进方向本质上都在尝试融合ReAct的灵活性和ReWOO的效率优势。

实际做技术选型时，我会先从用户需求出发分析场景特征。比如用户说要一个智能助手能回答产品问题，我会追问典型问题是什么，是FAQ类的标准问答还是开放式的咨询，数据源都有哪些，实时性要求多高，能接受的响应时间是多少。把这些需求转化成技术约束条件：如果百分之八十的问题都能从固定的几个数据源找到答案，那就是ReWOO的强项；如果问题类型很分散，经常需要多轮澄清用户意图，那就必须用ReAct。然后再考虑非功能需求比如成本预算、并发量、可维护性，最终选出最合适的方案。

我之前在课程项目里做过一个技术文档问答系统，最开始直接用了ReAct，发现回答一个问题经常要十几秒，体验很差。后来分析发现大部分问题其实查询路径都差不多，都是先检索相关文档片段，再提取关键信息，最后总结答案，完全可以提前规划。改用ReWOO之后响应时间降到了三四秒，虽然遇到特别复杂的问题准确率会下降一点，但整体用户满意度反而提升了，因为快速响应对用户体验的影响比完美准确更重要。这个经历让我深刻理解了选择技术方案时要综合考虑多个维度，而不是追求某个单一指标的极致。
